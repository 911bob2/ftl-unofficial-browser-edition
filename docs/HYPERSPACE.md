# Hyperspace in this engine

Behaviour reference for the Hyperspace (HS) port: what HS changes compared with the original game, when it applies,
and where the engine implements it. Code is ported from FTL-Hyperspace (GPL-3.0-or-later) commit 1b05a07, which
reports itself as HS 1.23.2 (its hooks are those of the 1.23.2 tag). Plan and interfaces: `.build/hs/PLAN.md` (I1-I5,
coordinator worktree). Status words are defined with the compatibility matrix below. Vanilla play never runs any of
this (see Gate).

## Gate (PLAN I2)

- `xyz.znix.xftl.hs.HS` is read once per engine start (`HS.init()` in `BrowserEngine.start`, before the game
  loads). `HS.modded` = the page set `window.ftlModSession` with at least one mod; `HS.active` = the session says
  `hyperspace` **and** the merged files contain `data/hyperspace.xml`; `HS.luaActive` is set by the Lua runtime,
  which starts in every Hyperspace session, mod scripts or not (docs/HS_LUA.md).
  Vanilla: all false, `HS.config == null`, and nothing below runs (each call site is one static field read).
- A session whose `hyperspace` flag disagrees with the files is recorded as `session` in the capability report.
- Capability report (`BrowserEngine.hsCapabilityReport()`): its `xml` and `xml-attr` rows are a gap list, the Hyperspace
  names a mod's XML uses that no engine source reads (`HsTagsUnread`, generated by `tools/hs-tags/gen-hs-unread.py`
  from `HsTags` and the sources; `--check` says whether it is current). On HS 1.23.2's names these are log and ini file
  names, text ids, `KEEP_COLORS`/`KEEP_INDICES` (no effect in HS either), the Discord `miniship(s)`/`appId` and
  `HACKING`, `hackLoopHS`, the artillery aim hotkey names. A name with a reader is not listed; how faithfully its feature
  works is the matrix below.

## hyperspace.xml settings (`HsConfig`)

`HsConfig.parse` reads `data/hyperspace.xml` exactly as `Global::PreInitializeResources` and
`Global::InitializeResources` (`src/game/Utilities/Resources.cpp`) do: the children of the `<FTL>` root in file
order, later nodes override earlier ones, booleans through `EventsParser::ParseBoolean` (`true`, `TRUE`, `True`
only, no trimming), element values untrimmed (rapidxml `value()`). A missing root, a parse failure or a missing file
leaves every setting at its default, as in HS. Attributes HS dereferences unchecked (e.g. `enabled`) are reported in
`HsConfig.problems` (HS would crash there) and the default is kept.

- **Version**: `<version>` `=x.y.z` exact, `~x.y.z` same major.minor and patch <= 1.23.2's, `^x.y.z` or no
  operator same major and (minor < 23, or minor 23 and patch <= 2); a value without dots is compared with the
  deprecated integer 332. HS's message on failure is kept in `versionMessage` and logged; loading continues. MV:
  `^1.19.0`, accepted. Verified against Resources.cpp by reading; unit check pending (no Kotlin unit runner).
- **Repeated nodes** (parity sweep M2, compared with Resources.cpp by reading): HS walks every root node and handles
  each wherever it stands, so every `<events>`, `<defaults>`, `<seeds>`, `<store>`, `<crew>`, `<augments>`, `<drones>`
  ... block counts. `HsSeeds` and the default lockdown read every block (`hsCoreProbe` checks both). Still read from the
  last block only: `customCredits`, `hullNumbers`, `hullBars`, `titleScreen` (HS parses each block over the previous
  one); no mod of the runner repeats them (Multiverse and its add-ons repeat `events`, `store`, `augments`, `crew`,
  `drones`, `version`, `discord`).
- **Errors** (parity sweep M2b, the original checked with the oracle's `ps-m2b` sessions): each pass runs in one `try`.
  A number `boost::lexical_cast` cannot read (strict: no spaces, the whole text) ends the pass it is in: the rest of
  that root node and every later root node of that pass are not read. The early pass's catch shows
  "Failed parsing hyperspace.xml" plus the cast's text, and an early error also skips the event files and the version
  check; the main pass's shows "Error parsing hyperspace.xml" plus the text, and skips PostProcessCustomEvents and
  later `<scripts>`. Without an early error, a `<version>` this HS does not accept (the last one counts; none counts as
  wrong) shows "Wrong version of Hyperspace detected ... You can continue, but mods may function incorrectly."; a
  version without three parts shows "Invalid/Unknown Hyperspace version check syntax ..." and ends the early pass.
  `HsConfig` models the casts it reads (version, `defaults` erosion and customLockdown, the typed options,
  `saveFile`) with `earlyStop`/`mainStop`, cuts the raw `nodes` and `passRoot` (events) where the pass stopped, keeps
  the bad value in the capability report's `problems` and lists the boxes in `errorBoxes` (also in the report).
  The boxes: HS's `ErrorMessage` is the system box "Error" with OK; the original shows it before the main menu over a
  black window and waits until OK, Enter or Escape closes it. Ours shows the same box (light grey, red error icon,
  the text, full-width OK; measured from the capture) before the first frame, one at a time, with the screen black:
  `web/hs-error-box.mjs` on the website, `HsErrorBox` on Android (Back closes it too). Not modelled: the casts inside
  other features' own parsers that have no `try` of their own (colors, customChoiceColors, systemPositions, the
  custom systems' levels, event-node parsers), the other start-up boxes HS shows (PostProcessCustomEvents' "Failed to
  load triggeredEventBox/timerSounds/warningMessage", recorded as `error` in the report) and an XML syntax error (our
  parser's message differs from rapidxml's; the report records `unparsable`). None of the runner's 15 mod sets shows a box.
- **Defaults** (HS source of each default): `CustomOptions.h` (`Setting<T>` = false/0 except `rightClickDoorOpening`
  true and `dismissSound` "airLoss"), `Balance.cpp` (hackingDroneFix true, repairDroneRecoveryFix true,
  controllableIonDroneFix false 6/6, hackingIonFix false), `CustomCrystalShard.cpp` (crystalShardFix true),
  `HullNumbers.cpp` (playerHpColorFix true), `CustomDrones.cpp` (defenseDroneFix off, box 150, ellipse 50, combat
  drones targetable), `Seeds.cpp` (seeds on, unlocks/achievements off, meta variables on), `CustomStore.cpp`
  (purchase limit 0/-16/60), `SaveFile.h` (prefix hs, inheritMode FORCE_OLD), `CustomShipSelect.h`,
  `CustomUpgrades.h`, `CommandConsole.h` (enabled false, invertCaps true), `ErosionEffect.cpp` (1/100/100/false).
- `<transformColorMode>` has no effect in HS 1.23.2 (Resources.cpp compares the node *name* with the mode names), so
  it is not read.
- Feature nodes (`ships`, `crew`, `events`, `augments`, `customSystems`, `store` (MV has two), `rewards`, `boss`,
  `drones`, `shipGenerators`, `victories`, `achievements`, `colors`, `languages`, `customCredits`, `titleScreen`,
  `hullNumbers`, `hullBars`, `targetableArtillery`, `alternateOxygenRendering`, `customTabs`, `customChoiceColors`,
  `sectorMap`, `discord`, `defaults`) are kept raw in `HsConfig.nodes` for the owning workstream.
- `<scripts><script>` paths in order: `HsConfig.scripts` (the Lua workstream runs them).

## Capability report (`HsCapability`, `BrowserEngine.hsCapabilityReport()`)

At engine start, HS sessions only:

1. **Rules**: every entry of `HsCapability.RULES` (the rule-level rows of the catalogue below) whose gate is on under
   the loaded config and that is not implemented is reported as `rule`.
2. **XML scan**: one regex pass over every merged `data/*.xml` (`ftl.browser.BrowserHsScan`, no DOM). Element names
   only HS reads (`HsTags.HS_ONLY_ELEMENTS`) are `xml`; HS-read attributes on vanilla elements that vanilla data
   never has are `xml-attr` (`element@attribute`); names neither vanilla nor HS read go to `ignored` (HS ignores
   them too; also shows names our tag tables miss). Top-level settings of `hyperspace.xml` are config (rules), not
   features. `HsTags` is generated by `tools/hs-tags/gen-hs-tags.py` from HS's parser code (string literals compared
   with node names, `first_node`/`first_attribute` arguments, string tables such as `StatBoost.cpp`'s stat names)
   minus the names vanilla data uses. Limitation: a vanilla element name used by HS in a new context is not seen.
3. **Load problems**: in modded sessions a vanilla loader that fails on an item drops that item and records `parse`
   (`HsLoad.item`); element names a vanilla loader rejects are skipped and listed as `ignored`
   (`HsLoad.skipUnknown`); files with several top-level elements (rapidxml accepts them, our DOM parser does not)
   are parsed wrapped in one `<FTL>` root (`HsLoad.parseXml`, counted in `xmlWrapped`). Such a file is found before
   any parse (`BrowserHsScan.needsRoot`: several top-level elements, text or CDATA outside the root, a late XML
   declaration; on MV's 1,240 data files it picks exactly the 1,048 a strict parser rejects), because a failing
   DOMParser call makes Chrome build a parsererror page with inline styles, which the page CSP reports as console
   errors. A file the check misses but the strict parser rejects is retried wrapped (`xmlWrappedLate`, MV: 0).
4. `lua` for each script while the Lua runtime is not up.
5. In play, modded sessions: a sector entry whose CreateEvent finds only consumed unique events (MV's
   `DROPPOINT_SUPPLY_DEPOT`) leaves its beacon without an event, as in FTL (LocationEvent nullptr; HS guards it in
   CreateLocation, RenderLabels and the map). The engine gives it `EventManager.hsNoEvent`: no text, choices or
   rewards, no random draws, saved by id. The HS map's shadowed drawing of such a beacon is not ported.

Workstreams mark what they implement with `HsCapability.implement("tag", "element@attr", ...)` and flip
`implemented` in `RULES`. JSON: `{modded, hyperspace, lua, modSet, hsVersion, config{version, versionOk, versionMessage,
problems, values{typed settings, node counts}}, xmlWrapped, unsupported[], byName[], ignored[], xmlWrappedLate}`; MV's current report: `.build/hs/reports/capability-mv.json`.

## Saves (PLAN I3, `xyz.znix.xftl.hs.save.HsSave`)

- Only when `HS.modded`: run (`InGameState.saveGameState`) and profile (`SaveProfile.save`) XML get a last child
  `<hyperspace modSet="<session hash>" hs="1.23.2">` (no `hs` for content-only sets) with one `<data key="...">` per
  registered key. Vanilla output is unchanged byte for byte (the call sites are behind `HS.modded`).
- `HsSave.verify` (MainGame.loadSavedGame, SaveProfile.load) refuses with `HsSave.Mismatch` and a player-facing
  message: a modded save in vanilla play, a vanilla save in a modded session, a save of another mod set. Vanilla
  play costs one child lookup. The loader also stores modded saves apart per mod set, so this is the second line.
- API: `HsSave.register(key, Scope.RUN|PROFILE, writer: (Element) -> Unit, reader: (Element?) -> Unit)`; readers run
  after the run/profile is loaded (null when the save has no block for the key).
- HS's own save files (`SaveFile.cpp`: `hs_<prefix>_prof.sav`, `inheritMode`): every save holds its own profile
  ([SAVES.md](SAVES.md)), so a new save starts fresh (inheritMode 2, FORCE_NEW); 0/1 (inherit or ask) are not used, by decision.

## Core rules implemented here

- `forceDlc` (CustomShipSelect.cpp `ShipBuilder::OnLoop`/`OnRender`): AE is forced on in the hangar and its toggle,
  box and title are not drawn (`HS.forceDlc()`; MainGame.switchToShipSelect/selectHangarMode, HangarPresentation).
- Crew names (CrewNames.cpp): in HS sessions `BlueprintManager::GetUnusedCrewName` draws one `random32()`, seeds a
  `std::mt19937` (`hs.Mt19937`, checked against the standard's 10000th-output vector 4123659995) and takes every
  name draw as `mt() >> 1` (`NativeCrewFactory.newName`). Not comparable with the oracle (its crew names are not
  deterministic, oracle report).
- Save check (`hsCoreProbe`, tests/hs-core.mjs): outside `<hyperspace>` a modded profile re-saves byte-identically;
  inside it the probe compares order-insensitively and reports a key whose data changes across save/load as a note
  (MV: meta variables reorder, a HashMap; `eventButtons` indices drift on reload).

## Events (`xyz.znix.xftl.hs.events`, `xyz.znix.xftl.hs.sector`)

Ported from FTL-Hyperspace (GPL-3.0-or-later) 1b05a07 `src/game/Gameplay/World/` (CustomEvents, TriggeredEvents,
CustomRewards, CustomSectors, Seeds); the files used are identical to 1.23.2. Every engine call site is guarded by
`game.eventManager.hs != null` (only HS sessions build an `HsEventParser`).

- **Loading** (`HsEventFiles`): hyperspace.xml `<defaults>` and the early `<events>` children, then
  `events_hyperspace.xml` and each `<eventFile>` before the vanilla files, then the rest of `<events>` and
  PostProcess. Every parsed event gets EventsParser::ProcessEvent's name (its own, or `PARENT n` from the global
  counter; `load` nodes take no number; a root node without a name, such as newEvents.xml's `<eventCounts>`, takes
  one as "Base Event: n") and its `CustomEvent` (`HsEventDefs`). A name defined again in the same file replaces
  the earlier event or ship; one an earlier file defined keeps that file's (AddEvents range-inserts each file's
  map), so MV's own files, which load first, override vanilla's. Lists and text lists: the last one wins. The HS
  tags (CustomEvent) always follow the last definition (ParseVanillaEventNode resets it).
- **Sector map and generation** (`HsSectorMap`, `HsGeneration`, `HsSeeds`): custom sector tree, StarMap
  GenerateMap/GenerateEvents rewrites, quest placement (`HsQuests`), the seeded-run streams (Seeds.cpp: run seed,
  sector map seed, quest seed per location, boss fleet seed). Generation uses `NativeRandom` only.
- **Event flow** (`HsFlow`, called from `DialogueWindow`): CreateLocation/UpdateLocation (revisit, loadEvent,
  loadEventList, queued/jump/death events, aliases, triggered events, restartEvent), CreateChoiceBox (requirement
  levels, `max_group`, choice types 0/1/2), ModifyResources (variables, removeItem, queues), CheckRequirements (the
  HS cost rule incl. the previous event, choiceRequiresCrew). Requirements: `HsReq` (variables, metaVariables,
  custom `<req>`, checkCargo, blueprint lists).
- **Variables** (`HsEvents`): playerVariables per run, metaVariables per profile. A new profile gets the initial
  meta variables once the event data is loaded (ScoreKeeper::WipeProfile); the initial player variables are rolled
